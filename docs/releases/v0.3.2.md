## v0.3.2 · The first recording after power-on no longer loses its start

This release fixes one thing: **the first recording after power-on missed about its first second** (#31, present since v0.3.0).

### Problem
- In recordings made on the device on 2026-10-21, the first memo recorded after power-on started with all zeros: 754 ms in the v0.3.0 one, 994 ms in the v0.3.1 one. The meetings recorded right after had none.
- The screen shows `● REC` as soon as recording starts. The user starts talking when they see it, so about the first second of speech was lost.
- The recording engine does not pad zeros; the zeros come from the microphone path.

### Cause (reproduced by the agent on the device, no user action needed)
- After power-up, from the first time it has a clock, the ES8311 forces the ADC output to 0 for 2^14 clock frames. At 16 kHz that is about 1 second.
  - At 32 / 48 / 64 kHz it is 497 / 332 / 249 ms. The frame count is the same.
  - The 754 ms in v0.3.0 also fits: its prompt tone played at 48 kHz for about 80 ms, which used up about 240 ms worth of 16 kHz frames first.
- Only power loss puts the codec back into this "cold" state. A soft reset of the ES8311 (REG00 = 0x1F) does too, with exactly the same result as a real power cycle.
- None of these make the codec cold: idle after `Mic.end` (from 1 s up to 40 minutes, it never did), an ESP32 restart, flashing.
- The device was always plugged into USB, so the codec was always powered. That is why HIL never caught it.
- None of the register settings we tried shorten this period. Only a higher clock rate does.

### Changes
1. **Warm-up at power-on**: after the audio task finishes its boot scan, it opens the microphone at 48 kHz for about 0.47 s, then closes it.
   - The warm-up makes no sound and writes no file.
   - On the bench, after warm-up, the next 16 kHz start had not a single forced sample (3/3, one of them after a 5 s gap).
   - A start pressed during warm-up is queued and waits at most about 0.5 s.
2. **Recording starts only when there is sound**: after recording starts, the screen shows `● REC` and the file starts being written only once the codec delivers the first block of sound that is not forced.
   - Forced blocks before it are dropped whole. Forced samples at the start of the first block with sound are trimmed too.
   - It waits at most 2 s. If there is still no sound after 2 s, recording starts anyway (a broken microphone must not stop you from recording) and a counter is incremented.
   - Releasing G0 while waiting discards the memo, the same as releasing during "preparing" before. A meeting can still be given a project tag during "preparing".
   - **What counts as "forced"**: at least 90% of a block (2048 samples, 128 ms) is the same value v, and |v| ≤ 2. Checking only for all zeros is not enough: M5Unified's DC-offset correction carries over between recordings, so the forced part is often a run of +1 or −1. At normal gain, room noise (RMS 12–14) never looks like this.
     - If there was a recording before the cold start, the forced part begins with a tail that slowly decays from about −DC to ±1 (the larger the DC, the longer; under 600 samples even at full scale). This tail does not count toward the 90%, and it is trimmed along with the start.
   - **All times count from the first written sample**: `at.up_ms` in `.M`, the position of ★, segment length and `lead_ms`.
     - When the codec is already warm, the first block is the `Mic.begin` transient, and writing starts from the first sample, as in v0.3.1. `lead_ms` is still 150, with the same meaning.
     - On a cold codec there is no transient; the 150 ms just skips a little more.
   - When the codec is already warm, `● REC` appears about one block (128 ms) later than in v0.3.1: it now waits for the first block of sound before showing.
3. **The test firmware adds `debug.codec{warm}`**, which replies `ack` (protocol v0 additive only; `v` is still 0).
   - With the microphone off, it soft-resets the ES8311, so the codec is as it was right after power-up. When `warm` is true it then runs the boot warm-up again, which simulates a real power-up.
   - While recording (including "preparing") it replies `E_BUSY` with `msg` `live`.
   - Release firmware does not know it and replies `E_UNKNOWN_TYPE`. `debug.codec` was added to the list checked by CI and the release check.
4. **New tests**:
   - HIL scenario `rec_cold_start`: the Mac's built-in speaker plays a continuous 1 kHz tone, and three memos are recorded.
     - Cold: after `debug.codec{warm:false}`.
     - Warm: right after.
     - Simulated power-up: after `debug.codec{warm:true}`.
     - Each one must have: no more than 20 ms forced at the start; the tone audible from the start; no more than 2.5 s from start to `● REC`. Also, the cold one must really be cold (at least 600 ms from start to `● REC`), and the simulated power-up one must already be warm (under 800 ms).
   - Device test `test_mic_cold`: the first start after a soft reset is forced, the start right after it is not, and a start after soft reset plus warm-up is not either. Needs no card and no tone.
5. Firmware version reports `cpa-fw/0.3.2`.

### Unchanged
- Gestures, rejection rules and the on-screen reasons, the 5-minute and 3-hour limits, ★ marks, silence throughout recording.
- Gain `kMicGain {9, 0xC4, 2}`, `lead_ms` 150, recording contract v1, segmentation, `file.*` transfer.
- Protocol v0 only gains `debug.codec` in the test firmware. Neither cpad nor WhisperWoof needs to change.

### Known issues
- **A real power-off and power-on was tested only once** (the 994.8 ms one in the #31 reproduction); the fix was verified with a soft reset that simulates power-up. Confirming the first memo after a real power cycle needs the user to switch off, unplug USB, power on again, and record a memo that starts speaking right away.
- **The 2 s counter is not visible yet**: when there is no sound for 2 s after start, the count is in `AudioTask::mute_timeouts()`. Device tests can read it; `debug.state` does not have it yet.
- The other issues listed for v0.3.1 still apply (meeting levels not measured separately, speech level measured only twice, #21, #22, #23, #14).

### Mac side and tools released in the same version
These were merged to main after v0.3.1, so they are also in the v0.3.2 tag; the firmware is not affected.
- **Claude Code hooks** (#33): `cpa hooks print` shows what would change first; only `cpa hooks install --yes` writes `~/.claude/settings.json`. Once installed, when a session needs permission, needs plan approval or asks a question, the board updates right away with the reason.
- **Why opening a session failed** (#25): when the folder is not trusted by the CLI or the CLI is not logged in, `cpa status` gives a one-off fix command.
- **Local data access** (#34): `cpa export` exports the whole archive (it refuses iCloud and other cloud-synced folders); `cpa mcp serve` is a local stdio MCP server, read-only by default, with no network port; `cpa mcp setup claude-code|codex|cursor|claude-desktop` prints the config. ChatGPT can only connect to public HTTPS, so it is not supported.
- **Host simulator** (#32): `firmware/sim` runs the firmware on the Mac, producing screenshots with the real font, or acting as a virtual device for cpad and HIL tests.
