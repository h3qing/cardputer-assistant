# 10 · v0.2.0 (M2) work packages

> Generated by the M2 design workflow on 2026-10-20 and finalised after review. The design basis is [09-m2-design.md](09-m2-design.md); implementation agents take their tasks from this file.

> M2-A and M2-C own non-overlapping directories and can be developed in parallel. M2-B depends on both. M2-D is real-device HIL and depends on M2-B and M2-C.

## Defaults the Lead has already decided (requirement: keep questions to a minimum)

- Storage: SD is the primary store, with the internal `cpafs` as the fallback; keep the `CPA_STORAGE_NO_SD` switch as a way back.
- Release file names: `cpa-<tag>.bin` (merged image, shown as cpa-<tag> in Launcher) and `cpa-<tag>-app.bin`.
- v0.2 does not offer formatting the SD card on the device.
- Launcher uses the user-approved stable release **2.9.1** (official release asset, 1,422,720 B); after download, check the size first, then record the SHA-256.
- If Launcher's own SD driver cannot read this 512GB card, use Launcher's serial install instead (`flash overwrite`); ask the user before proposing a fix upstream.
- Pulling the card while running: v0.2 does not switch stores automatically; it only shows a notice and never lets the main loop get stuck.
- The protocol only adds the optional fields `hello.store` and `hello.launcher`; `v` stays 0.
- Pending items on the SD card are plaintext, as in v0.1; encryption and a PIN lock are deferred and noted in SECURITY.md.

(2) Partition table and build config.

(3) lib/storage (pure code, no Arduino, M5, esp_, SD or LittleFS headers).
- storage_plan.{h,cpp}: PartFacts, SdState{Disabled,Absent,Unusable,Ok}, SdFacts{state,size_mib}, Store, StoreNote{None,NoCard,SdUnusable,NoInternal,LegacyTable,NoStorage}, StoragePlan, plan_storage(), lfs_shards(), strictly per the table in 09 §3.4.
- sd_paths.{h,cpp}: two-way mapping between logical and physical paths (09 §3.5): /outbox/<E>-<B>-<S>.json ↔ <root>/outbox/<E>/<B><first 3 of S>.J<last 1 of S>; bad goes under BAD/<E>/ the same way; .tmp has no mapping; other paths get root prepended.
- fat_port.h: FatErr{None,NotFound,Exists,Disk,Other} and the FatPort interface (09 §3.3).
- sd_store.{h,cpp}: SdStore : FileStore, constructed with FatPort& and root (default /cpa). prepare() creates root and root/outbox and does a probe write (write 1 byte to PROBE.BIN, sync_close, unlink). open_write, on NotFound, creates the parent directories level by level and tries once more. list("/outbox") reports the bad directory, lists the epoch directories one by one (at most 8, only one directory open at a time) and joins file names back into <MonoId>.json; other names are reported as they are. rename() returns false straight away without calling port; atomic_rename() is false. On the first FatErr::Disk it locks up: after that every method fails at once and never calls port again. free_bytes() is 0xFFFFFFFF normally and 0 once locked; failed() reports the lock.
- null_store.h: every operation fails, free_bytes() is 0.

(4) lib/outbox.
- file_store.h adds virtual bool atomic_rename() const, default true.
- Add store_commit.{h,cpp}: commit_file and move_file (table in 09 §3.6). Under FAT semantics rename is never called. move_file uses a static 2KB read buffer.
- outbox_io's persist, apply and the scan's MoveToBad now call them. Keep the function names outbox_persist / outbox_apply (the chains in scripts/stack_budget.py refer to them).
- The boot scan gets two new rules, active only when !fs.atomic_rename(): delete a .json of length 0; only count a .tmp, do not delete it. Behaviour on LittleFS is identical to v0.1, word for word.
- Add outbox_migrate.{h,cpp}: MigrateResult{moved,failed}, MigrateObserver. For each id: read the source (static 2KB) → commit_file to the target → delete the source. On any failure keep the source and continue. bad/ is not migrated. Satisfies the invariants in 09 §3.7.
- No function frame exceeds 1536B; large buffers are always static, with the reason in a comment (same precedent as outbox_io).

(5) Test support.
- FakeStore gains a FAT mode (set_fat(true)): atomic_rename() returns false; rename fails if the target exists; it counts rename calls. Default mode behaves as before, so the v0.1 tests are unaffected.
- Add a shared power object so two FakeStores lose power together at global step k.
- Add fake_fat_port.h: physical files and directories in memory; can inject Disk / NotFound and other errors on the k-th call; counts calls per method.
- stack_gate.py adds storage to LIBS, plus the new chains in the pure libraries (commit_file, move_file, outbox_migrate, SdStore reads and writes).

(6) hal.
- sd_card.{h,cpp}: SdFacts hal_sd_mount(SdStore&), strictly following the mount steps in 09 §3.9. With CPA_STORAGE_NO_SD defined, report Disabled and do not touch the bus. SPI.begin(40,39,14,12); sdcard_init(12,&SPI,20MHz); sdcard_mount(pdrv,"/sd",2,false). On failure read sdcard_type(): NONE/UNKNOWN is Absent, SD/SDHC/MMC is Unusable; in neither case call sdcard_uninit or retry. On success compute size_mib, then call store.prepare(); if that fails report Unusable. VfsFatPort: POSIX calls with a /sd prefix, errno mapped to FatErr (EIO/ENODEV/ENXIO→Disk, ENOENT→NotFound, EEXIST→Exists, anything else→Other).
- lfs_store: the label becomes cpafs. The begin() signature is unchanged (no arguments): if cpafs is not found, return false without mounting or formatting. If found, the shard count comes from lfs_shards(size); if it cannot mount, format only cpafs itself. With 4 shards, the Crockford value of the last MonoId character modulo 4 gives _0–_3; with 32, keep the v0.1 mapping. Never touch spiffs.
- part_facts.{h,cpp}: per 09 §4.3, only collect facts, make no judgements.

(7) Device tests: test_sd_store (root is /cpatest, deleted afterwards), test_sd_absent (run by hand with the card pulled), and an updated test_storage; contents in 09 §9.2.

Not in scope: src/main.cpp, Runtime, shell, UI, protocol, daemon, scripts/, CI and release, README, formatting the SD card on the device, switching stores at run time, v0.3 recording. Do not change v0.1's test/core/test_outbox_boot_scan and test/core/test_outbox_core.

## M2-B · Firmware integration, UI and Launcher release: choosing the store and migrating at boot, NoStorage, system page, budget and partition scripts, release artifacts, README

### Scope

Implement per docs/09-m2-design.md. The work is as follows.

(1) Boot order in src/main.cpp, per 09 §3.1.
- Call hal_part_facts, hal_sd_mount(g_sd), g_lfs.begin(), plan_storage in that order.

- When a save, outbox_apply or a project-cache write fails, the storage error count goes up by 1.

(3) SysInfo in lib/module_api gains fields: store, sd state, sd size, launcher, cpafs size, note, migrated, migrate_failed, store_errors.

(4) System page in modules/system: per 09 §8, add the boot method and storage rows, text for each StoreNote, and the migration and storage error counts; adjust the row limit to match.

(5) scripts (tests in test_scripts.py first for all of them).

## M2-D · HIL: SD, migration and Launcher scenarios; 07 manual checklist (G-L1–G-L9, SD items)

- **Owned paths**: `tools/hil/`, `docs/07-hil-checklist.md`
- **Depends on**: M2-B, M2-C

### Scope

Implement per docs/09-m2-design.md §9.3 and §9.4. The work is as follows.

(1) tools/hil/scenarios/storage.py.

(2) tools/hil/scenarios/launcher.py.

## Open questions (raised during design; we proceed with the defaults above)

- Primary vs secondary store: the design defaults to SD as the outbox's primary store, for three reasons: under Launcher cpafs is only 448KB; with the 8.3 layout on SD, save p95 is about 29ms; and it also fixes v0.1's slowness with a 200-item backlog. The cost is that 0 loss on FAT power cuts can only be proven at the protocol level; 10 manual power cuts are low-strength evidence. If the power-cut gate shows any loss, the release can fall back to "internal as primary" with the existing CPA_STORAGE_NO_SD switch. sd-card.md originally suggested keeping the v0.2 outbox on LittleFS. Go with the default (SD primary)?
- Release file names: the default becomes cpa-<tag>.bin (merged image, shown as cpa-v0.2.0 in Launcher) and cpa-<tag>-app.bin, no longer v0.1's cpa-fw-…-full.bin naming. OK?
- Formatting SD on the device: by default v0.2 does not do it. This dev card is already FAT32, and you have authorised wiping and reformatting it at any time. New cards of 32GB and up ship as exFAT and need diskutil eraseDisk FAT32 CPA MBRFormat /dev/diskN run once on a Mac first. Should v0.2 already offer formatting on the device? That needs two confirmations, blocks the main loop for about 1 minute (44 seconds measured on the 512GB card), and restarts automatically when done.
- Launcher version: do HIL and README pin the beta (2026-10-15, built from e8cc4df, with the macOS USB-drive fix and DDLB) or the stable 2.9.1? The beta download URL gets overwritten by new builds, so we would need to keep our own fixed copy.
- Launcher's own SD driver very likely cannot read this 512GB card either (the same ACMD41 problem). If G-L1 fails, which path: install from a different card under 32GB, use Launcher's serial flasher, or propose fixes upstream to bmorcelli/Launcher and arduino-esp32? Submitting publicly upstream needs your consent.
- Pulling the card while running: v0.2 does not switch stores automatically. The one operation that discovers the error after the card is pulled stalls for 0.6–2 seconds; after that the card is not touched again. Saves fail until a restart (with a notice), and pending items on the card are sent after the next boot with the card in. Acceptable?
- Things that need your hands, and when they can be scheduled: (a) provide 2–3 other cards, at least one under 32GB that ships as FAT32; (b) 10 manual power cuts (flip the switch and unplug); (c) boot once with the card pulled to time a cardless boot; pull the card once while running to see whether keys still respond; (d) put the dev card in a Mac card reader, reformat it with diskutil and re-run the device tests (wiping is authorised by you). Do you have a card reader at hand? (e) install Launcher for the G-L gates (web flasher, or written by an agent with esptool).
- Should the protocol add the two optional fields hello.store and hello.launcher (additive only, v unchanged, ignored by the v0.1 daemon)? Added by default, so HIL can confirm a scenario really went through SD, and so cpa status can show why a save failed.
- The PRD originally put "SD card history archive + Mac public-key encrypted wrapper" and "PIN lock" in v0.2; both are deferred. Until then, pending items on SD are plaintext, the same as in v0.1's internal flash, except that the card can be pulled out and read directly. Acceptable?
