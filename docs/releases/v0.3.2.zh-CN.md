## v0.3.2 · 开机后的第一条录音不再丢开头

这一版只修一件事：**开机后的第一次录音，开头约 1 秒录不到**（#31，v0.3.0 起就有）。

### 问题
- 2026-10-21 设备上的录音里，开机后录的第一条便条开头全是 0：v0.3.0 那条 754 ms，v0.3.1 那条 994 ms。紧接着录的会议都没有。
- 屏幕一开始录音就显示 `● REC`，用户看到就开口，所以开头约 1 秒的话丢了。
- 录音引擎不补零，0 来自麦克风这一路。

### 原因（agent 在设备上复现，不用用户动手）
- ES8311 上电以后，从第一次有时钟起，会把 ADC 输出压成 0，一共 2^14 个时钟帧。16 kHz 下就是约 1 秒。
  - 32 / 48 / 64 kHz 下分别是 497 / 332 / 249 ms，帧数都一样。
  - v0.3.0 的 754 ms 也对得上：它的提示音用 48 kHz 放了约 80 ms，等于先用掉了约 240 ms 的 16 kHz 帧。
- 只有断电会让 codec 回到这个"冷"状态。ES8311 的软复位（REG00 = 0x1F）也会，而且和真断电的结果一模一样。
- 下面这些都不会让 codec 变冷：`Mic.end` 之后的空闲（放了 1 s 到 40 分钟都不会）、ESP32 重启、刷机。
- 设备一直插着 USB，codec 一直通电，所以 HIL 一直没测出来。
- 试过的寄存器设置都不能缩短这段时间，只有提高时钟频率能缩短。

### 改动
1. **开机预热**：音频任务做完开机扫描后，用 48 kHz 开麦克风约 0.47 s，然后关上。
   - 预热不出声，也不写文件。
   - 台架上预热以后，下一次 16 kHz 开始没有一个样本被压住（3/3，其中一次隔了 5 s）。
   - 预热期间按下的开始先排队，最多等约 0.5 s。
2. **等到有声音才算开始**：开始录音以后，要等 codec 送来第一块没被压住的声音，屏幕才显示 `● REC`、才开始写文件。
   - 前面被压住的块整块丢掉，第一块有声音的块里开头被压住的样本也裁掉。
   - 最多等 2 s。2 s 还没有声音也照常开始（麦克风坏了也不能因此录不了），并且记一次数。
   - 在等的时候松开 G0，便条被丢弃，和以前在"准备"时松手一样。会议在"准备"时照样可以打项目标签。
   - **"被压住"的判定**：一块（2048 个样本，128 ms）里至少 90% 是同一个值 v，而且 |v| ≤ 2。不能只看全是 0：M5Unified 的直流偏移校正会跨录音保留，被压住的部分常常是一串 +1 或 −1。正常增益下房间底噪（RMS 12–14）不会这样。
     - 冷启动前录过音时，被压住的部分先是一段从约 −DC 慢慢衰减到 ±1 的尾巴（DC 越大越长，满幅时也不到 600 个样本）。这段尾巴不算进 90%，裁掉开头时也一起裁掉。
   - **时间都从写下的第一个样本算**：`.M` 的 `at.up_ms`、★ 的位置、段长和 `lead_ms`。
     - codec 已经预热过时，第一块就是 `Mic.begin` 的冲击，和 v0.3.1 一样从第一个样本写起。`lead_ms` 仍是 150，含义不变。
     - codec 冷启动时没有冲击，150 ms 只是多跳过一点。
   - codec 已经预热过时，`● REC` 比 v0.3.1 晚约一块（128 ms）出现：现在等第一块声音到了才显示。
3. **测试固件新增 `debug.codec{warm}`**，回 `ack`（协议 v0 只新增，`v` 仍为 0）。
   - 麦克风关着时对 ES8311 软复位，codec 回到刚上电的样子。`warm` 为 true 时再跑一遍开机预热，等于模拟一次真正的上电。
   - 正在录音（包括"准备"）时回 `E_BUSY`，`msg` 为 `live`。
   - 正式固件不认识它，回 `E_UNKNOWN_TYPE`。CI 和 release 检查的名单加上了 `debug.codec`。
4. **新测试**：
   - HIL 场景 `rec_cold_start`：Mac 内置扬声器放连续的 1 kHz 音，录三条便条。
     - 冷：`debug.codec{warm:false}` 之后。
     - 暖：紧接着。
     - 模拟上电：`debug.codec{warm:true}` 之后。
     - 每条都要求：开头被压住的部分不超过 20 ms；开头就听得到那个音；开始到 `● REC` 不超过 2.5 s。另外，冷的那条必须真的冷（开始到 `● REC` 至少 600 ms），模拟上电那条必须已经预热好（不到 800 ms）。
   - 设备测试 `test_mic_cold`：软复位后第一次开始被压住，紧接着的一次没有，软复位后先预热再开始也没有。不用卡，也不用放音。
5. 固件版本报 `cpa-fw/0.3.2`。

### 没有变的
- 手势、拒绝规则和屏幕上的原因、5 分钟和 3 小时的上限、★ 标记、录音全程不出声。
- 增益 `kMicGain {9, 0xC4, 2}`、`lead_ms` 150、录音契约 v1、分段、`file.*` 传输。
- 协议 v0 只多了测试固件的 `debug.codec`。cpad 和 WhisperWoof 都不用改。

### 验证
- 主机侧（2026-10-21 真机测试之后，agent 按 `ci.yml` 在本机把四个 job 的每一步都跑了一遍，全部通过）：
  - 固件 native 测试 438 个，覆盖率 97%（gcovr，hal 和 usb_transport 除外；`mic_start.cpp` 100%）。
  - 协议工具测试 248 个，录音契约测试 87 个；向量检查通过（测试固件 27 种消息，多了 `debug.codec`；15 个流程）。
  - daemon 测试 854 个，覆盖率 96.8%；HIL 工具测试 360 个。
  - 正式固件 946,448 B（v0.3.1 是 945,312 B），里面找不到任何 `debug.*` 钩子（和 CI 同样的检查）；测试固件和 10 个设备测试都能编译。
- 真机（2026-10-21 17:20–17:32，agent，设备一直插着 USB，详见 07 号文档 §6.10）：
  - `test_mic_cold` 3 次都 PASS（每次 4/4）：软复位后被压住 7 块（896 ms），紧接着 0 块，预热（491 ms）以后 0 块。三次的数字完全一样。
  - `test_mic_gain`、`test_rec_budget` 都 PASS。
  - `rec_cold_start` 跑了 4 次，12 条便条开头被压住的都是 0 ms。"开始到 `● REC`"：冷 1,128–1,143 ms，暖 134–150 ms，模拟上电 134–147 ms。
    - 第 1 次 12/15。Mac 的音量现在是 25（#31 复现时是 69），音到设备只有约 −55 dBFS，三条的"开头听得到音"（≥ −50 dBFS）都不过。但每条开头 250 ms 的音和后面稳定段只差 0.12 dB 以内，所以开头没被压住，只是音太轻。
    - 第 2–4 次把音文件从 −20 dBFS 提到 −1 dBFS（系统音量没改），音到设备约 −44 dBFS，3 次都是 15/15。
    - 开头冲击：暖和模拟上电那两条，前 150 ms 峰值 3,387–5,242（约 −20 到 −16 dBFS），之后最大 368，和 v0.3.1 同一量级。冷的那条没有冲击：前 150 ms 峰值 94–264，稳定段 105–313。
  - 录音回归 8/8 PASS（`sd_empty`、`sd_store`、`sd_bulk`、`handshake`、`capture`、`rec_memo`、`rec_meeting`、`rec_resume`）。`rec_memo` 从 G0 按下到第一个样本 525 ms（v0.3.1 是 506 ms）。
  - `mic_verify` 没跑成。音量 25 时 B1 探测的音 A 只有 −62.07 dBFS（v0.3.1 时是 −44.52），参考声音放大到上限也到不了 −48，场景第一步就停了（设备已重启，卡已清空）。`kMicGain` 这一版没改，`test_mic_gain` 也通过了。要重跑，得先把音量调回 69。
  - 刷回正式版：app 946,448 B，里面没有 `debug.*`。之后 `cpa status` 显示 `link: ready`、`fw=cpa-fw/0.3.2`，卡上 0 段。

### 已知问题
- **真正断电再上电只测过一次**（#31 的复现里那一次 994.8 ms），修复是用软复位模拟上电验证的。要确认真断电后的第一条便条，需要用户关掉开关、拔掉 USB 再开机，录一条开头就说话的便条。
- **2 s 的计数还看不到**：开始后 2 s 都没有声音时，计数在 `AudioTask::mute_timeouts()`，设备测试能读，`debug.state` 里还没有。
- v0.3.1 列出的其余问题照旧（会议的电平没有单独测、说话音量只测过两次、#21、#22、#23、#14）。

### 同一个版本里一起发布的 Mac 端和工具
这些在 v0.3.1 之后已经合进 main，所以也包含在 v0.3.2 的 tag 里；固件不受影响。
- **Claude Code hooks**（#33）：`cpa hooks print` 先看会改什么，`cpa hooks install --yes` 才写入 `~/.claude/settings.json`。装上以后，session 要权限、要审批计划、提问时，看板马上更新并带上原因。
- **开 session 失败的原因**（#25）：目录没被 CLI 信任、CLI 没登录，`cpa status` 会给出一次性的修复命令。
- **本地数据访问**（#34）：`cpa export` 导出整个档案（拒绝 iCloud 等云同步目录）；`cpa mcp serve` 是本地 stdio MCP 服务，默认只读、不开网络端口，`cpa mcp setup claude-code|codex|cursor|claude-desktop` 打印配置。ChatGPT 只能接公网 HTTPS，不支持。
- **主机模拟器**（#32）：`firmware/sim` 在 Mac 上跑固件，出真实字体的截图，或做一个虚拟设备给 cpad 和 HIL 测试用。
